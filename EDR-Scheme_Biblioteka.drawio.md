# Практична робота №1: Моделювання даних і вибір підходу
## Система управління бібліотекою

---

## 1. ОПИС ПРЕДМЕТНОЇ ОБЛАСТІ

### Назва системи
**Система управління бібліотекою (Library Management System)**

### Користувачі системи:
1. **Бібліотекар** — додає/видаляє книги, видає книги читачам, фіксує повернення, розраховує штрафи за затримку
2. **Читач** — шукає книги за категоріями, видає книги, повертає книги, переглядає історію видачі
3. **Адміністратор** — управляє користувачами (бібліотекарями, читачами), генерує звіти, налаштовує параметри системи

### Описувані об'єкти:
- **КНИГА** — видання в бібліотеці (з унікальним інвентарним номером)
- **АВТОР** — творець книги
- **ВИДАВЕЦЬ** — організація, що видала книгу
- **КАТЕГОРІЯ** — жанр/тема книги (художня, навчальна, наукова тощо)
- **ЧИТАЧ** — людина, що позичає книги
- **ВИДАЧА** — факт видачі книги читачу з датою повернення
- **ПОЛИЦЯ** — місце зберігання книги в бібліотеці

### Основні операції:
1. ✓ Додавання нової книги в каталог
2. ✓ Реєстрація нового читача
3. ✓ Видача книги читачу
4. ✓ Повернення книги в бібліотеку
5. ✓ Пошук книг за категоріями, автором, видавцем
6. ✓ Розрахунок штрафів за затримку повернення
7. ✓ Генерація звітів про найпопулярніші книги

## 3. ТАБЛИЦЯ «ОБ'ЄКТ — ФАКТ — СЦЕНАРІЙ»

### Сценарій 1: Додати нову книгу в каталог

| Об'єкт   | Факт                      | Що відбувається |
|----------|---------------------------|-----------------|
| КНИГА    | ID книги                  | **Створюється** (новий унікальний номер) |
| КНИГА    | Назва книги               | **Створюється** (вводить бібліотекар) |
| КНИГА    | Рік видання               | **Створюється** (вводить бібліотекар) |
| КНИГА    | Кількість сторінок        | **Створюється** (вводить бібліотекар) |
| КНИГА    | Статус книги              | **Встановлюється** на "доступна" |
| КНИГА    | Полиця зберігання         | **Створюється** (призначається полиця) |
| АВТОР    | ID автора                 | **Знаходиться** (існуючий) або **Створюється** (новий) |
| ВИДАВЕЦЬ | ID видавця                | **Знаходиться** (існуючий) або **Створюється** (новий) |
| КАТЕГОРІЯ| ID категорії              | **Вибирається** (розпиковується зі списку) |

### Сценарій 2: Видати книгу читачу

| Об'єкт   | Факт                      | Що відбувається |
|----------|---------------------------|-----------------|
| КНИГА    | Статус книги              | **Змінюється** з "доступна" → "видана" |
| КНИГА    | Полиця зберігання         | Залишається незмінною (для поточної видачі) |
| ВИДАЧА   | ID видачі                 | **Створюється** (новий запис) |
| ВИДАЧА   | Дата видачі               | **Встановлюється** на поточну дату |
| ВИДАЧА   | Планова дата повернення   | **Розраховується** (поточна дата + 30 днів) |
| ВИДАЧА   | Фактична дата повернення  | **Встановлюється** як NULL (поки не повернена) |
| ВИДАЧА   | Статус видачі             | **Встановлюється** на "активна" |
| ВИДАЧА   | Сума штрафу               | **Встановлюється** на 0 (поки не прострочена) |
| ЧИТАЧ    | ID читача                 | **Вибирається** (читач шукається в системі) |

## 4. ПОРІВНЯННЯ МОДЕЛЕЙ ДАНИХ ДЛЯ БІБЛІОТЕКИ

### 4.1 Ієрархічна модель
**Сильна сторона:** Природна ієрархія читач → видача → книга відповідає структурі системи. Швидкий доступ до історії видач одного читача.

**Слаба сторона:** Не можемо показати, що одна книга видавалась БАГАТЬОМ читачам без дублювання даних. Видавці і категорії важко інтегрувати в чітку ієрархію.

---

### 4.2 Мережева модель
**Сильна сторона:** Добре моделює зв'язки «багато-до-багатьох»: одна книга → багато видач, один читач → багато видач, книга → кілька авторів.

**Слаба сторона:** Складна для розробки і розуміння. Запити на пошук найпопулярніших книг або читачів зі штрафами потребують складної навігації по мережі.

---

### 4.3 Реляційна модель ✓ РЕКОМЕНДУЄТЬСЯ
**Сильна сторона:** Ідеально моделює наш випадок: таблиця ВИДАЧА посилається на КНИГА і ЧИТАЧ (FK), легко розраховуються штрафи за запитом. Простий SQL для пошуку, фільтрації та звітів.

**Слаба сторона:** Нормалізація даних потребує багато таблиць, що може ускладнити деякі складні запити. Потребує JOIN операцій для багатьох запитів.

---

### 4.4 Об'єктна модель
**Сильна сторона:** Клас Книга містить методи (пошук за категорією, розрахунок штрафу), що природно відповідає задачам. Успадкування: Видача успадковує Резервування.

**Слаба сторона:** Як зберігати об'єкти в базі даних? Потребує ORM (Hibernate, SQLAlchemy), що додає складність. Штрафи за затримку - це не властивість об'єкта, а результат бізнес-логіки.

---

### 4.5 Документна модель (MongoDB, CouchDB)
**Сильна сторона:** Один документ = одна видача з усіма даними (ID книги, ID читача, дати). Гнучкість: можемо додати поле "коментар" без міграції схеми. Швидко масштабується.

**Слаба сторона:** Дублювання даних: 100 видач однієї популярної книги дублюють всю інформацію про книгу. Складно оновити інформацію про книгу - потрібно оновити 100 документів. Пошук «всі книги ЦЬОГО автора» потребує скану всіх документів.

---

### 4.6 Модель ключ-значення (Redis, Memcached)
**Сильна сторона:** Дуже швидкі операції читання. Вдала для кешування: "популярні книги на цей тиждень", "активні видачі читача".

**Слаба сторона:** Немає запитів або фільтрації. Як знайти "всі книги категорії 'Фантастика'"? Як розрахувати штрафи за затримку для 10 000 читачів? Потрібна вторинна база даних (наприклад, SQL) для основних операцій.

---

## 5. ОБҐРУНТУВАННЯ ВИБОРУ МОДЕЛІ ДАНИХ

**Обрана модель:** **РЕЛЯЦІЙНА** (SQL: PostgreSQL, MySQL, SQLite)

### Аргументація:

1. **Зв'язки «багато-до-багатьох»:** Система має складні зв'язки (одна книга → багато видач, один читач → багато видач, книга → кілька авторів). Реляційна модель з первинними та зовнішніми ключами ідеально це моделює.

2. **ACID гарантії:** При видачі книги критично важливо атомарно оновити статус книги та створити запис видачі. SQL транзакції гарантують цілісність даних.

3. **Складні запити:** Розрахунок штрафів за затримку, пошук популярних авторів, генерація звітів - все це легко вирішується SQL запитами з JOIN та агрегацією.

4. **Нормалізація:** Безпеку даних: інформація про автора зберігається один раз, тому не буває суперечливих даних про дату народження.

5. **Масштабованість:** PostgreSQL добре масштабується на мільйони видач без деградації продуктивності.

6. **Простота розробки:** Розробники добре знають SQL та ORM фреймворки (SQLAlchemy, Django ORM), що пришвидшує розробку.

Ієрархічна та мережева моделі занадто обмежені, об'єктна потребує ORM, документна суході дублювання, ключ-значення - непридатна для основних операцій.

## 6. ПИТАННЯ ДЛЯ ЗАХИСТУ

### 1. Чим дані відрізняються від інформації та знань?

**Дані** — необроблені факти (приклад: «854tb», «2026-09-09»).
**Інформація** — обробленні дані із контекстом (приклад: «Читач 854tb зареєстровано 2026-09-09»).
**Знання** — правила та закономірності із інформації (приклад: «якщо видача просрочена більш ніж на 7 днів, застосувати штраф 50 грн/день»).

### 2. Які функції СКБД вам знадобляться для обраної системи?

- **Зберігання** — таблиці для книг, читачів, видач
- **Пошук і фільтрація** — знайти книги за категорією, автором
- **Актуальність** — оновлення статусу книги під час видачі
- **Обчислення** — автоматичний розрахунок штрафів за формулою
- **Цілісність** — зовнішні ключі забезпечують, що видача посилається лише на існуючу книгу
- **Конкурентність** — декілька бібліотекарів видають книги одночасно
- **Резервна копія** — відновлення даних при відмові

### 3. Чому один і той самий факт може бути збережено з помилкою за кількома адресами?

У документній моделі: інформація про книгу "Война и мир" дублюється в кожному документі видачі. Якщо потім вибрано рік видання на 2024 замість 1869, потрібно оновити 500 документів. Якщо оновили лише 400, то дані суперечливі і система видає неправильну інформацію.

### 4. Які критерії використали для вибору моделі даних?

- Складність зв'язків між об'єктами
- Потребу в ACID гарантіях під час видачі
- Складність запитів (JOIN, агрегація)
- Потреба в нормалізації (уникнення дублювання)
- Знання розробників і доступність інструментів

## ВИСНОВОК

Для системи управління бібліотекою **реляційна модель даних** є оптимальним вибором. Вона забезпечує надійне зберігання зв'язків між книгами, читачами, видачами та штрафами, дозволяє виконувати складні запити для пошуку та аналізу, гарантує цілісність даних через первинні та зовнішні ключі, та підтримує конкурентність коли декілька користувачів працюють одночасно. Хоча мережева модель теоретично могла б моделювати зв'язки, вона складна у використанні, а документна модель призводить до дублювання даних. Таким чином, використання SQL СКБД (PostgreSQL, MySQL або SQLite) є практичним і надійним рішенням для реалізації такої системи.
